## What 100% does and does not mean

Read this before quoting the number.

- **It is the rate on these files, and the corpus already found bugs.** The first Enron run scored 99.9853%.
  Both groups of failures were real, and both were fixed, so 100% is partly the result of looking at this
  exact corpus. A new corpus can be expected to find more.
- **108 cells are excluded, not parsed.** They are data tables, which have no formula text to parse and which
  M2 reports as an unsupported feature.
- **Enron's formula text is POI's rendering of Excel's binary tokens, not text Excel stored** (ADR-0013). So
  this rate partly measures that rendering, which is more regular than what a person types.
- **Parsing is not correctness.** Round-tripping shows that the printer and parser agree with each other. Only
  M2's comparison with cached values can show that the tree means what Excel means.
- **164 of 616 Enron files (27%) were not read at all:** 141 are not OLE2 files despite the extension, and 23 are
  older than BIFF8, which POI does not read. They are counted as rejected and contribute no formulas.
- **The real-world sample is small and uneven.** The cleaned subset has 452 readable files. No two are
  byte-identical, but some are clearly variants of one template: 9 files account for all 9,000 `XIRR` calls.

## What the corpus found

| First result | Cause | Fix |
|---|---|---|
| 108 cells: "Formula has no text" | Data-table cells. POI's usermodel throws `Could not get ArrayRecord` on them, and my reader had swallowed the exception, so the run also wrongly reported 0 data tables | Read the raw `TABLE` records. All 108 fall inside one, which confirms the cause |
| 14 cells such as `#REF!B167` | Excel writes this after a referenced sheet is deleted. The parser did not accept it | `BrokenRef` keeps the address as written, and it evaluates to `#REF!` |
| `excessiveNestingIsADiagnosticNotACrash` overflowed the stack on one run | The limit of 512 levels is about 7,700 frames, close to a 1 MB stack, so the result depended on JIT state. It had passed by luck | The limit is now 128 (Excel allows 64 nested functions), and `parse` catches `StackOverflowError`, since formula text is untrusted |

```
$ ./gradlew build
```

`RoundTripProperties` (jqwik) generates expressions and checks that printing and reparsing gives the same tree.
It caught a real bug during development: `Exprs.withoutSpans` left inner spans in place.

## Regression gates

`eval/baseline-enron.properties` and `eval/baseline-poi.properties` hold floors for files loaded, formula cells,
parse rate, round-trip failures, crashes, and, for Enron, data tables. `make eval` fails below any of them, and
CI runs `make eval`, so a metric can drop only by editing one of those files.

The floors on files and cells stop a run that checks too little from passing, which was the lesson of M0's
false pass (ADR-0011).

## Not proven

- Any meaning. Nothing is evaluated until M2.
- Formula text as stored by Excel at real-world scale: Enron is `.xls`, and the `.xlsx` corpus is POI's test data.
- Structured references parse as opaque text, and dynamic-array syntax has had little exposure, because 2000s-era
  Enron files cannot contain either.

## Process disclosure

The house rule asks for failing tests first. The first parser commit (`31d1f6b`) added signatures and tests, but
Error Prone rejected the stubs, so **those tests never ran red**. The commit message says so. Afterwards, the
`#REF!B167` tests were run and seen failing before the fix.

Windows note: `corpus/download.sh` starts several processes per file. With 969 files and little free memory,
that failed here with `fork: retry`, and the job was stopped by the memory guard. Files were verified
afterwards in one process: 616 and 353 verified, 0 failed. Linux CI runs the script as written.
