# M4 walkthrough: Truffle runtime and benchmarks

**State: exit checks pass. CI status is recorded in `docs/PROGRESS.md`.**

Output is copied from CI runs on 2026-11-06, for `02b8ab3`: `bench` `42251602885`, `eval` `42251602610`. Design: `docs/design/truffle.md`.

## The finding to read first

**The JIT gave no measured speed benefit.** Formulas really do compile on GraalVM CE, and they give the same answers, but the Truffle
engine was no faster than the plain interpreter on the one model benchmarked. M4's exit check asks for agreement and published
benchmarks, and both are met. It does not ask for a JIT speedup, and there is none to report.

So "JIT-compiled" in the tagline is true of what runs on a GraalVM JDK, but it is not yet a reason to expect speed. The lead over Apache POI
comes from the evaluator design, and shows up with the interpreter alone. The CLI's default stays the interpreter.

## Exit check 1: Truffle equals the interpreter on the whole corpus

`make differential` compares value and status on every formula cell of every workbook, and fails on any disagreement.

On Temurin 25, where Truffle runs without a JIT:

```
differential on Interpreted, OpenJDK 64-Bit Server VM 25.0.5
784 files, 0 timed out, 0 crashed
860666 formula cells compared, 0 disagreements {}
19711 shapes, 88090 nodes built, 170 delegated to the interpreter (0.19%)
```

On GraalVM CE 25, with low thresholds so that compiled code actually runs:

```

784 files, 0 timed out, 0 crashed
860666 formula cells compared, 0 disagreements {}
19711 shapes, 88090 nodes built, 170 delegated to the interpreter (0.19%)
```

## Exit check 2: JMH against Apache POI, with methodology and hardware

Results, methodology, hardware, and limits are in [`docs/benchmarks/README.md`](../benchmarks/README.md). In milliseconds per operation on GraalVM CE:

| Operation | Interpreter | Truffle | Apache POI |
|---|---|---|---|
| Full recalculation | 14.17 ± 1.86 | 16.19 ± 0.86 | 67.57 ± 2.42 |
| One input changed | 0.611 ± 0.016 | 0.589 ± 0.033 | 16.36 ± 9.24 |

These come from a **shared CI runner and one synthetic model**, so they are labeled noisy. A run on a quiet machine would be worth having.

## What 0 disagreements does and does not mean

- **It tests evaluating the tree, not functions.** Both engines call the same function library, so a bug in `SUM` would appear in both.
  Fidelity against Excel is what checks that.
- **860,666 includes cells neither engine calculates.** Most of Enron's external-link formulas get the same status and cached value from both.
  The share actually calculated is about the 48% covered in M2 on Enron, and higher on POI.
- **Not every cell ran compiled code.** 3,677 compilations happened, but which cells ran compiled is not recorded. Rarely used shapes stayed
  interpreted, even with low thresholds.
- **Delegating to the interpreter cannot disagree.** Only 0.19% of nodes delegate, but those subtrees are not really being checked.
- **It is one evaluation order, with no volatile functions calculated.** `IncrementalWorkbook` through Truffle has a unit test, but no corpus
  differential.

## What this milestone settled

- **ADR-0006's open points.** `new RootNode(null)`, with no `TruffleLanguage`, compiles at Tier 1 and Tier 2 on GraalVM CE, on the class path and
  the module path. Truffle 25.0.5 worked with GraalVM CE 25.0.2. The class path works, so it stays the simple choice for now.
- **The shape of nodes.** A target per cell would rarely get hot, so formulas with one R1C1 shape share a target. On the corpus, that is 19,711 shapes
  for 860,666 cells, and it cut nodes from 2,108,339 to 88,090.
- **Hand-written specialization** in place of the Truffle DSL (ADR-0018).

## Known limits

- `cellerity bench` is not implemented. It still says so, and `make bench` runs the benchmarks on a generated model. Benchmarking a user's own workbook
  is not available.
- Truffle is reachable from the CLI only through `verify --engine truffle`.
- A JVM warning about `sun.misc.Unsafe` from Truffle appears on JDK 25.
- Values stay boxed, and each cell read crosses a boundary, which may be why the JIT does not help. That has not been profiled.
